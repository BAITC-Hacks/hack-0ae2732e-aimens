# Инструкции для агентов: MVP AI Sana / HackAlem

## Цель проекта

Построить за соревновательные 5 часов запускаемое веб-приложение для практических бизнес-задач. Полный путь в приложении: слабое описание бизнеса → минимум три уместных уточняющих вопроса → редактируемая и подтверждённая карточка → объяснимый рейтинг → публикация в общем каталоге → отклик студенческой команды → ручной выбор бизнеса → подтверждённый первый результат и баллы команды. Каждый переход должен работать в коде, а не только на слайдах.

Работайте небольшими проверяемыми шагами. В первую очередь доведите этот путь до запуска; затем улучшайте интерфейс и второстепенные сценарии. Описание результата должно соответствовать тому, что действительно работает.

Эти баллы относятся к **оценке проекта жюри**, а не к рейтингу задачи внутри приложения.
3. `HACKALEM_STRUCTURE.md` — организационный контекст HackAlem, включая работу в выданном организатором репозитории, почасовой прогресс и запуск по README. Документ кейса назван AI Sana и указывает другой допустимый размер команды. Не выдавайте их за один официальный документ; при реальной сдаче сверяйте действующие инструкции организатора.
4. `README.md` и `docs/` — документация работающего демо: команды запуска, архитектура, AI-контракт и сценарий показа. Обновляйте её при изменении поведения.

При расхождении локальных материалов с новыми официальными условиями зафиксируйте различие и примените опубликованные условия конкретной задачи. Не меняйте критерии или модель продукта по догадке.

## Технологические решения

- Next.js App Router, TypeScript, Tailwind CSS, Zod; один Node.js процесс.
- SQLite через встроенный `node:sqlite`, без ORM. Серверные обработчики работают в Node runtime. Файл базы сохраняется между перезапусками.
- OpenAI Responses API для анализа описания; модель по умолчанию `gpt-4.1-mini-2025-04-14`, меняется серверной переменной окружения.
- Vitest для правил и серверных операций; Playwright для основного пути в браузере.
- Планируемые зоны кода: `src/app` — страницы и HTTP-обработчики, `src/domain` — типы и чистые правила, `src/server` — база, операции и AI. До написания кода проверьте существующие файлы и следуйте уже созданным контрактам.
- Интерфейс на русском для ноутбука: светлый фон, тёмная типографика, существующий зелёный акцент, ясные подписи и числовые состояния. По актуальному указанию владельца устаревшие дизайн-документы не являются требованиями; текущую палитру сохранять. В MVP четыре основных поверхности: каталог, конструктор задачи, карточка задачи, кабинет бизнеса.

Приложение уже создано. Используйте скрипты `dev`, `build`, `start`, `test`, `test:e2e`, `lint`, `typecheck` из `package.json` и сохраняйте lockfile. Требуется Node.js 24.x. E2E работают на порту 3100 с отдельной временной базой; рабочая база — `data/praktika.sqlite`. Не называйте команду проверенной, пока она реально не прошла.

## Неприкосновенные правила продукта

### Карточка и рейтинг

- Карточка включает название, тему, исходное описание, контекст, потребность, пользователей, данные и доступ к ним, ограничения, ожидаемый результат, показатель успеха и целевое значение, контакт и формат взаимодействия.
- `computeReadiness(card)` — одна чистая функция для предварительного показа и серверного пересчёта. Она возвращает итог 0–100, уровень, разбивку баллов и список недостающих сведений. Клиент не присылает серверу готовый рейтинг как источник истины.
- Веса: контекст 10, потребность 10, данные **вместе со способом доступа** 20, ожидаемый результат 15, показатель **вместе с целевым значением** 15, ограничения 10, пользователи 10, контакт 5, взаимодействие 5. Пробелы и пустые значения дают 0. Для данных «нет» и «не уточнено» дают 0.
- Уровни: 0–39 «Черновик», 40–69 «Рабочая», 70–89 «Готовая», 90–100 «Приоритетная». Рейтинг показывает полноту подтверждённой задачи; он не подтверждает истинность текста и не зависит от известности компании.
- До ручного подтверждения изменения остаются предварительными. Сохранение подтверждённых полей и их нового рейтинга выполняйте вместе. Для публикации нужны название, тема и явное подтверждение. Низкий рейтинг не блокирует публикацию или отклик.

### Каталог, предложения и прогресс

- Все опубликованные задачи видны каждой демокоманде. Фильтры по теме и уровню готовности меняют только представление. Сортировка: рейтинг по убыванию, затем более ранняя публикация, затем идентификатор.
- Команда отправляет идею, план, срок и ссылку на прототип. Не устанавливайте лимит количества предложений. Статусы: `pending`, `selected`, `rejected`.
- Бизнес выбирает или отклоняет предложения вручную. Он может выбрать 0, 1 или несколько команд; выбор одной не отклоняет остальные. AI не назначает исполнителей.
- Выбранная команда отправляет описание и ссылку на «Первый результат». Только подтверждение этого результата бизнесом даёт **10 баллов**. Начисление уникально для пары «задача — команда»; повторный запрос и несколько предложений одной команды не увеличивают награду. Отправка отклика и выбор команды баллов не дают.

### AI и локальный резерв

- Вход AI: исходное описание, тема и уже введённые сведения. Выход: предложенные значения с фрагментом источника, недостающие поля и 3–5 вопросов, привязанных к полям.
- Модель не может добавлять факты. Применяйте извлечённое значение лишь при подтверждённом совпадении фрагмента с текстом пользователя; сомнительное оставляйте пустым. Сохраняйте ответы пользователя редактируемыми. Ничего не публикуйте автоматически.
- Используйте структурированный ответ и проверяйте его на сервере. При отсутствии ключа, тайм-ауте 20 секунд, отказе или некорректном ответе показывайте **явно обозначенный** локальный режим: находите недостающие поля правилами приложения и задавайте по ним 3–5 вопросов. Этот режим должен работать на новых вводах, а не возвращать заранее заготовленную карточку.
- Сохраняйте ввод при ошибке AI. Ключ живёт только в серверном окружении; `.env` и реальные токены не попадают в репозиторий. Документируйте промпт, формат входа/выхода и пример некорректного ответа.

## Работа и проверка

1. Согласуйте типы `Task`, `Team`, `Proposal`, `Progress` и данные одной рабочей вертикали. Затем соберите путь «создать → подтвердить → опубликовать → откликнуться → выбрать → подтвердить результат».
2. Подготовьте идемпотентные синтетические данные: минимум 5 исходных черновиков, 5 опубликованных карточек с разными уровнями, 5 команд и 5 предложений. Повторная инициализация не дублирует их и не стирает пользовательские записи.
3. После каждого законченного шага проверьте соответствующий путь. При работе в официальном репозитории фиксируйте реальный промежуточный результат по итогам каждого соревновательного часа. Не переносите готовую основную функциональность, созданную до официального старта, если правила хакатона это запрещают.
4. Перед сдачей выполните `npm ci`, `npm run build`, `npm test`, `npm run test:e2e` и `npm run lint` в чистом окружении. Проверьте перезапуск с сохранением данных и запуск без личных аккаунтов и API-ключа.
5. В README укажите точные команды, версии, `.env.example`, архитектуру, формулу рейтинга, правила каталога, демоданные, проверку полного сценария, внешние компоненты и известные ограничения. README должен позволять эксперту проверить проект самостоятельно.

Содержательные тесты: 0/100 и границы 39/40, 69/70, 89/90; публикация и отклик при низком рейтинге; отсутствие публичных изменений до подтверждения; два выбранных предложения; отсутствие двойного начисления; ошибка AI без потери ввода; сохранение данных после перезапуска; полный путь в браузере за пять минут. Не подменяйте проверку скриншотами или заглушками.

## Объём MVP

Для демонстрации используйте переключатель «Бизнес / команда», без настоящей регистрации. Не добавляйте чат, уведомления, файловое хранилище, календарь, сложный трекер, векторную базу, обучение модели или инфраструктуру продакшена. Добавляйте зависимости только тогда, когда они помогают закрыть обязательный сценарий. Исправляйте сбои основного пути прежде визуальных мелочей.

Для Demo Day подготовьте показ на одном примере: бизнес описывает проблему списания выпечки, уточняет сведения, показывает рост рейтинга, публикует задачу; команда отправляет предложение; бизнес выбирает её и подтверждает первый результат. Демонстрация должна показывать работу приложения, а не имитировать переходы презентацией.
