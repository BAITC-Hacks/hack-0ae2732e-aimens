## Правила, которые определяют работу команды

1. Один участник — одна команда и один проект. Один проект подаётся по одной выбранной задаче.
2. Все участники обязаны лично присутствовать на площадке в период соревнования. Временный выход — с разрешения организатора; обычный предел отсутствия 60 минут.
3. Основная функциональность проекта должна быть создана с 13:00 до 18:00 23 сентября. Готовый до старта продукт подавать нельзя. Разрешены подготовленные инструменты, библиотеки, шаблоны и инфраструктура, если они не составляют основное решение. Сторонние компоненты и лицензии нужно раскрыть.
4. Основная разработка должна идти в **GitHub-репозитории, созданном организатором через edu.astanahub.com**. Закрытый внешний репозиторий для основной работы запрещён. Требуется подтверждаемый промежуточный результат по итогам **каждого часа**.
5. Итог фиксируется в 18:00. Поздние изменения при оценке не учитываются.
6. README должен объяснять назначение, архитектуру, технологии, зависимости, установку, запуск, переменные окружения и проверку основного сценария. Если эксперт не сможет запустить проект по README, команда не проходит дальше; поздние исправления не принимаются. Для внешних сервисов нужен способ проверки без личных аккаунтов участников.
7. AI-инструменты и агенты разрешены. Пункт 5.4.12 положения говорит, что **Codex не обязателен**, если обратное не указано в конкретной задаче. Лендинг, напротив, указывает использование Codex как условие. Этот конфликт следует уточнить в официальном канале; до уточнения разумно предусмотреть использование Codex.
8. В техническом отборе действуют критерии конкретной задачи, опубликованные до начала соревнования. На Demo Day ориентиры жюри: ценность — 25, результат и качество — 20, инновационность — 15, масштабирование — 20, презентация/демо/ответы — 20. Итоговые места определяет коллективное решение жюри, а не только сумма баллов.
9. Положение предусматривает единый зачёт и до 10 основных призовых мест, без квот по задачам.
10. По положению организатор получает безвозмездное право использования результатов без ограничения территории и срока, включая публикацию, модификацию и передачу третьим лицам. Это важно учитывать при выборе данных и сторонних материалов.

## Структура принятия решения по задаче

После получения доступа к заданиям заполнить по каждому кандидату одну карточку:

```text
Трек / задача:
Постановщик и пользователь:
Проблема и требуемый результат:
Входные данные и доступность:
Обязательные технологии / ограничения:
Критерии и баллы технической оценки:
Минимальный сквозной сценарий для демо:
Что можно сделать за 5 часов:
Как эксперт запустит проект без команды:
Риски (данные, API, интеграции, лицензии):
Роли 1–3 участников:
```

Выбирать задачу по вероятности завершить **запускаемый сквозной сценарий**, соответствию опубликованным критериям и доступности данных. Пока задания скрыты, ранжировать треки по шансам на победу нельзя.

## Рабочая структура проекта

В день соревнования развернуть её в **предоставленном организатором репозитории** после официального старта. Это схема, а не заранее готовая основная функциональность.

```text
/
  README.md                 # запуск и проверка за несколько минут
  .env.example              # имена переменных, без секретов
  docs/
    task.md                 # точная формулировка задачи и критерии
    architecture.md         # схема компонентов и поток данных
    sources.md              # внешние модели, данные, код, лицензии
    demo.md                 # сценарий показа и контрольные примеры
    progress.md             # результаты каждого часа
  app/                      # интерфейс и основной сценарий
  tests/                    # ключевые проверки сценария
  data/sample/              # разрешённые обезличенные тестовые данные
```

Рекомендуемый ритм пяти часов:

| Время | Результат |
|---|---|
| 13:00–14:00 | Выбрана одна задача, зафиксированы критерии, создан каркас и первый работающий сценарий |
| 14:00–15:00 | Данные, основной обработчик, первый end-to-end результат |
| 15:00–16:00 | Ключевой AI/агентный шаг, проверка результата на примерах |
| 16:00–17:00 | Интерфейс, обработка ошибок, демонстрационные данные |
| 17:00–18:00 | Чистый запуск по README, проверка критериев, демо, финальный push до 18:00 |

По окончании каждого часа зафиксировать промежуточный результат в репозитории и `docs/progress.md`.
